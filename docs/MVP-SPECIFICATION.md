# Syncora — Спецификация MVP

## 1. Общая информация

- **Название проекта:** Syncora.
- **Тип проекта:** приложение для совместного планирования времени и встреч.
- **Формат MVP:** desktop-приложение на Avalonia с backend API на .NET 8 и базой данных PostgreSQL.
- **Основная задача:** предоставить пользователю календарь, возможность добавлять людей и совместные календари, а также автоматически находить общее свободное время для встречи нескольких участников.

Syncora не должна быть копией обычного календаря. Основное преимущество продукта — **автоматический поиск времени, удобного для всех выбранных участников**.

## 2. Цель и задачи MVP

Цель MVP — проверить основную продуктовую гипотезу: пользователю проще указать участников, длительность и период поиска, чем вручную сравнивать несколько календарей.

- Регистрация и авторизация пользователей.
- Создание личных и совместных календарей.
- Добавление других пользователей.
- Совместные календари до 10 участников.
- Три уровня доступа: просмотр, редактирование, свободен/занят.
- Создание, изменение и удаление событий.
- Настройка рабочего времени и часового пояса.
- Автоматический поиск общего свободного времени.
- Создание встречи на найденном временном интервале.
- Внутренние уведомления.
- Совместные списки покупок.
- Адаптивный интерфейс Avalonia для изменения размеров окна.

## 3. Технологический стек

| Компонент | Технология |
|---|---|
| Backend | .NET 8 / ASP.NET Core Web API |
| Язык | C# |
| ORM | Entity Framework Core |
| База данных | PostgreSQL |
| Desktop Client | Avalonia UI |
| Архитектура клиента | MVVM |
| Авторизация | JWT |
| API | REST / JSON |
| Документация API | Swagger / OpenAPI |
| Тестирование | xUnit |
| Контейнеризация | Docker Compose |
| Cache | Redis — опционально |

Redis в MVP не является обязательным. На первом этапе приложение должно работать без Redis. Его можно добавить позднее для кэширования, rate limiting, временных данных и оптимизации поиска при росте нагрузки.

Для MVP не использовать микросервисную архитектуру. Backend реализуется как единое ASP.NET Core приложение.

## 4. Пользовательские роли и доступ

В системе должен существовать владелец календаря и его участники.

### 4.1. Уровни доступа

| Роль | Возможности |
|---|---|
| OWNER | Полное управление календарём и участниками. |
| EDITOR | Просмотр и изменение событий. |
| VIEWER | Только просмотр событий. |
| FREE_BUSY | Видит только состояние «свободен/занят». |

Режим FREE_BUSY является обязательным для приватности. Пользователь с таким доступом не должен видеть название, описание или другие детали чужого события.

### 5.1. Регистрация

- Пароль.

После регистрации автоматически создаётся личный календарь пользователя.

### 5.2. Авторизация

### 5.3. User

## 6. Календари

Один пользователь может иметь несколько календарей: Личный, Работа, Семья, Друзья, Проект, другие пользовательские календари.

Каждый календарь имеет название, цвет, тип, владельца, участников и настройки доступа.

### 6.1. Типы

- PERSONAL — личный календарь.
- GROUP — совместный календарь.

### 6.2. Ограничение

Совместный календарь может содержать не более 10 пользователей, включая владельца.

### 6.3. Создание календаря

Пользователь указывает название, цвет и тип календаря. Для GROUP после создания можно добавлять участников.

## 7. Люди и участники

В разделе «Люди» пользователь может искать зарегистрированных пользователей и добавлять их в свои совместные календари.

GET /api/users/search?query=ivan

Для пользователя отображаются имя, email и общие календари в пределах разрешённого доступа.

При добавлении участника система проверяет, что он ещё не добавлен и лимит в 10 человек не превышен.

## 8. События

Событие принадлежит календарю и содержит временной интервал.

Id, CalendarId, CreatorId, Title, Description, StartAt, EndAt, CreatedAt, UpdatedAt

### 8.1. Создание события

- Название.
- Дата.
- Время начала.
- Время окончания.
- Календарь.
- Описание — необязательно.

### 8.2. API

- GET    /api/events
- GET    /api/events/{id}
- POST   /api/events
- PUT    /api/events/{id}
- DELETE /api/events/{id}

При создании и изменении события backend проверяет права пользователя и корректность StartAt/EndAt.

## 9. Главная функция «Сформировать встречу»

Кнопка «Сформировать встречу» является центральным элементом MVP и должна быть визуально заметной на основном экране.

### 9.1. Ввод параметров

- От 2 до 10 участников.
- Длительность встречи.
- Дата или период поиска.
- Время начала поиска.
- Время окончания поиска.

### 9.2. Длительность

15 минут, 30 минут, 45 минут, 1 час, 1,5 часа, 2 часа, 3 часа, 4 часа, произвольная длительность в минутах.

### 9.3. Период

Сегодня, Завтра, Выбранная дата, Эта неделя, Произвольный диапазон.

### 9.4. Пример

Пользователь выбирает 4 участников, длительность 4 часа и пятницу. После нажатия «Найти время» система анализирует расписание всех участников и возвращает ближайшие интервалы, в которых все участники свободны.

## 10. Алгоритм поиска свободного времени

Алгоритм должен быть детерминированным и простым для MVP. Использование AI не требуется.

1. Получить выбранных участников.
2. Получить события их календарей за заданный период.
3. Получить рабочие часы каждого участника.
4. Привести даты к единому представлению времени.
5. Сформировать занятые интервалы каждого участника.
6. Получить свободные интервалы с учётом рабочего времени.
7. Вычислить пересечение свободных интервалов всех участников.
8. Оставить интервалы, продолжительность которых не меньше требуемой.
9. Отсортировать результаты по ближайшей дате и времени.
10. Вернуть пользователю, например, первые 5 подходящих вариантов.

### 10.1. Важное правило

Время вне рабочего графика пользователя не считается доступным стандартным временем, даже если в его календаре нет событий.

### 10.2. Повторная проверка

Перед окончательным созданием встречи backend обязан повторно проверить занятость всех участников. Это защищает от ситуации, когда свободный слот был занят другим событием после выполнения поиска.

## 11. Подтверждение и управление встречами

После выбора временного интервала пользователь видит дату, время, длительность и список участников.

После нажатия «Подтвердить» создаётся Meeting и записи MeetingParticipant.

- POST /api/meetings/search
- POST /api/meetings

### 11.1. Meeting

Id, CreatorId, Title, StartAt, EndAt, CreatedAt, UpdatedAt

### 11.2. MeetingParticipant

Id, MeetingId, UserId, Status

Статусы: PENDING, ACCEPTED, DECLINED.

Для простоты MVP встреча после подтверждения создателем считается созданной, а участникам создаются уведомления.

## 12. Уведомления

MVP должен поддерживать внутренние уведомления:

- Приглашение на встречу.
- Создание встречи.
- Изменение встречи.
- Удаление или отмена встречи.
- Приглашение в совместный календарь.

Id, UserId, Type, Title, Message, IsRead, CreatedAt

### 13.1. Список

### 13.2. Элемент списка

### 13.3. Возможности

- Создание списка.
- Добавление товара.
- Изменение товара.
- Удаление товара.
- Изменение количества.
- Отметка товара как купленного.

### 13.4. API

## 14. Настройки рабочего времени и часового пояса

Пользователь должен иметь возможность указать часовой пояс и рабочие часы.

### 14.1. Часовой пояс

Все даты и время рекомендуется хранить на backend в UTC. На клиенте время отображается в часовом поясе пользователя.

### 14.2. Рабочее время

По умолчанию можно использовать понедельник–пятница 09:00–18:00. Пользователь может изменить расписание.

## 15. Интерфейс и требования к Avalonia

Интерфейс MVP должен соответствовать предоставленному референсу: светлый фон, фиолетовая акцентная система, скруглённые карточки, левое меню, центральная область календаря и правая панель поиска встречи.

### 15.1. Основной экран

```
┌──────────────┬─────────────────────────┬────────────────────┐
│ Sidebar      │ Calendar                │ Right Panel        │
│              │                         │                    │
│ Календарь    │ Апрель 2025             │ Сформировать       │
│ Встречи      │ Пн Вт Ср Чт Пт Сб Вс    │ встречу            │
│ Списки       │                         │                    │
│ покупок      │ 09:00                   │ Участники          │
│ Люди         │ [Событие]               │                    │
│ Настройки    │ 10:00                   │ Доступные слоты    │
│              │                         │                    │
│ Мои          │                         │ 10:00–11:00        │
│ календари    │                         │ 12:00–13:00        │
└──────────────┴─────────────────────────┴────────────────────┘
```

### 15.2. Навигация

- Календарь.
- Встречи.
- Списки покупок.
- Люди.
- Настройки.

### 15.3. Календарь

- День.
- Неделя.
- Месяц.

Для MVP основным рабочим режимом рекомендуется сделать неделю. Остальные режимы могут быть реализованы как дополнительные.

### 15.4. Цвета

Основной акцент — фиолетовый. Для разных календарей допускаются отдельные цвета: личный, рабочий, семейный, друзья и т. д.

### 15.5. Адаптивность

Интерфейс должен корректно перестраиваться при изменении размера окна. Основная desktop-композиция: Sidebar | Calendar | Right Panel.

## 16. Backend и архитектура

Backend реализуется как монолитное ASP.NET Core Web API на .NET 8.

```
Syncora
├── Syncora.Api
│   ├── Controllers
│   ├── Services
│   ├── DTO
│   ├── Middleware
│   └── Migrations
└── Syncora.Client

    ├── ViewModels
```

Рекомендуется придерживаться разделения Domain, Infrastructure, API и Client, но не превращать проект в сложную многоуровневую архитектуру без необходимости.

## 19. Безопасность

- HTTPS.
- JWT-аутентификация.
- Хранение паролей только в виде безопасного хэша.
- Проверка прав доступа на каждом защищённом endpoint.
- Валидация входных данных.
- Rate limiting.
- Защита от доступа к чужим календарям по идентификатору.
- Секреты production не хранить в Git.
- Логирование ошибок без вывода чувствительных данных.

Если пользователь не является участником календаря или не имеет необходимых прав, API должен вернуть 403 Forbidden.

```json
{
  "error": {
    "code": "CALENDAR_ACCESS_DENIED",
    "message": "У вас нет доступа к этому календарю."
  }
}
```

### 20.2. Integration Tests

- Регистрация.
- Авторизация.
- Создание календаря.
- Добавление участника.
- Создание события.
- Поиск свободного времени.
- Создание встречи.
- Проверка прав доступа.

### 20.3. Критические тесты Meeting Engine

Пример: A свободен 10:00–14:00, B свободен 12:00–16:00, длительность 2 часа. Система должна вернуть 12:00–14:00.

Пример: A свободен 10:00–12:00, B свободен 11:00–12:00, длительность 2 часа. Система не должна вернуть слот.

## 21. Docker и запуск

Для локальной разработки использовать Docker Compose.

```yaml
services:
  postgres:
    image: postgres

  redis:
    image: redis
    # optional
```

API и Avalonia-клиент могут запускаться непосредственно из среды разработки .NET.

Миграции Entity Framework Core должны быть частью процесса развёртывания базы данных.

## 22. Нефункциональные требования

- Обычные API-запросы должны выполняться ориентировочно менее чем за 500 мс при нормальной нагрузке.
- Поиск свободного времени для 10 участников и разумного диапазона дат должен выполняться без необходимости Redis.
- Backend должен быть stateless.
- Ошибки API должны возвращаться в стандартизированном JSON-формате.
- Пользователь не должен видеть stack trace.
- Приложение должно корректно обрабатывать потерю соединения с API.
- Все операции с базой должны выполняться через Entity Framework Core.

## 23. Что не входит в MVP

- Микросервисная архитектура.
- Kubernetes.
- Kafka.
- Сложный AI-рекомендатель.
- Видеоконференции.
- Полноценная корпоративная CRM.
- Сложная система биллинга.
- Расширенная BI-аналитика.
- Сложные публичные ссылки на календари.
- Сложная система recurring events.
- Интеграции Google Calendar, Outlook и Apple Calendar — рекомендуется оставить следующим этапом.
- Нативные push/email-интеграции — можно добавить после стабилизации основного сценария.
